## 0. Quick answer to the memorable claim

**User recollection:** “any LALR(n) can be rewritten into LALR(1)”

**More precise statement (theory):**

1. **Language level (Knuth 1965):** For every *k* ≥ 1, a language has an LR(*k*) grammar
   iff it is a deterministic context-free language (DCFL) iff it has an LR(1) grammar.
   So **every LR(*k*) language is an LR(1) language.**
   Source: Knuth, *On the Translation of Languages from Left to Right* (1965);
   Wikipedia “LR parser” theory section summarizing Knuth.

2. **Grammar level (Mickunas, Lancaster, Schneider 1976):** There is a **mechanical
   transformation** that takes an arbitrary **LR(*k*) grammar** and produces an
   **equivalent LR(1) grammar** (same language; different nonterminals/productions;
   possibly much larger). Same paper also: prefix-free LR(*k*) → LR(0); LR(1) → SLR(1)
   → (1,1) BRC under further transforms.
   Source: Mickunas et al., *Transforming LR(k) Grammars to LR(1), SLR(1), and (1,1)
   Bounded Right-Context Grammars*, JACM 23(3), 1976, pp. 511–533.
   PDF often used in courses: https://www.cs.sfu.ca/~anoop/courses/CMPT-379-Spring-2004/lrk_xform.pdf

3. **LALR is not the same as LR:** LALR(1) is a **grammar-class / automaton-construction**
   restriction (merge LR(1) states with same core). A grammar can be **LR(1) but not
   LALR(1)**. Merging can reintroduce conflicts. So:
   - “Any **LR(*k*) grammar** → **LR(1) grammar**” is classical and solid.
   - “Any **LALR(*k*) grammar** → **LALR(1) grammar**” is **not** the standard clean theorem
     people quote; the safe language claim is DCFL / LR(1). If you need the power of
     LR(1) after LALR merge fails, use **canonical LR(1)**, **IELR(1)** (selective split),
     or a **different LALR(1) grammar** for the same language (hand or auto rewrite).
   - Informal claims exist (e.g. old comp.compilers threads) that LALR(*k*) can be rewritten
     as LALR(1); treat as folklore unless you re-derive under the LALR merge semantics.

4. **Ambiguous grammars:** If the *language* is not deterministic (or the *grammar* is
   inherently ambiguous in a way that no equivalent deterministic grammar preserves
   the intended tree shape without external priorities), **no *k* and no pure rewrite**
   gives deterministic LALR/LR tables. Tools then use **precedence/associativity**,
   **predicates**, or **nondeterministic** parsers (GLR, Earley, ALL(*), GLL).

**Bottom line for slyce:** The user’s memory is **directionally right for LR(*k*)→LR(1)
languages/grammars**, not a free pass that “any surface LALR(*n*) model magically becomes
LALR(1) with the same AST shape.” Rewrite **changes structure**; you need a **cover**
or **tree map** back to the human model.

## 1. Hierarchy (grammar classes)

Rough inclusion (standard textbook picture):

```
LR(0) ⊂ SLR(1) ⊂ LALR(1) ⊂ LR(1) = LR(k) for k≥1  (as LANGUAGE classes for LR(k)/LR(1))
```

More carefully:

| Class | What it is | Practical notes |
|-------|------------|-----------------|
| LR(0) | Reduce without lookahead | Rare for full languages; needs prefix property |
| SLR(1) | LR(0) states + Follow sets for reduce | Weak; many false conflicts |
| LALR(1) | Merge LR(1) states with same core; precise prop. lookaheads | yacc/bison/happy default-ish |
| Canonical LR(1) | Full item+lookahead states, no merge | Menhir default; larger tables |
| LR(*k*) | *k* tokens of lookahead | Rare in tools; transform to LR(1) preferred |
| GLR | Explore all LR actions | Handles ambiguity; super-linear worst case |
| IELR(1) | LALR base + split states only when needed | Bison option; LR(1) power, smaller than full LR(1) |

Sources:
- Wikipedia: LR parser, LALR parser, Canonical LR parser
- Dragon Book (Aho/Sethi/Ullman / Aho/Lam/Sethi/Ullman)
- Bison docs: `%define lr.type ielr` (IELR)

**Important:** LR(*k*) **languages** collapse to LR(1) for *k*≥1.  
**Grammars** do not: a natural LR(2) grammar of a language may not be LR(1) *as written*.

## 2. Knuth: languages, not just grammars

Knuth (1965) introduced LR(*k*) and showed efficiency: linear-time parsing for LR(*k*).

Key theorem (paraphrased, widely cited):

> For every *k* ≥ 1, a language can be generated by an LR(*k*) grammar  
> **iff** it is deterministic (context-free)  
> **iff** it can be generated by an LR(1) grammar.

Implications:
- You never *need* LR(*k*) *parser tables* for *k*>1 at the language level if you are willing
  to **change the grammar**.
- Changing the grammar **changes derivation trees** unless you maintain a cover/mapping.

Sources:
- D. E. Knuth, *On the Translation of Languages from Left to Right*, Information and Control, 1965.
- Wikipedia “LR parser” Theory section:
  https://en.wikipedia.org/wiki/LR_parser
- Aho & Ullman, *The Theory of Parsing, Translation, and Compiling* (classic detailed treatment).

## 3. Mickunas et al. 1976: mechanical LR(*k*) → LR(1) grammar transform

### 3.1 Claim of the paper

> “A method is presented for **directly transforming an arbitrary LR(*k*) grammar to an
> equivalent LR(1) grammar**.”

Also:
- Prefix-free LR(*k*) → equivalent LR(0)
- Method can take LR(1) → SLR(1) → (1,1) bounded right-context

Citation:
- M. D. Mickunas, R. L. Lancaster, V. B. Schneider,  
  *Transforming LR(k) Grammars to LR(1), SLR(1), and (1,1) Bounded Right-Context Grammars*,  
  Journal of the ACM, Vol. 23, No. 3, July 1976, pp. 511–533.  
  ACM: https://dl.acm.org/doi/10.1145/321958.321972  
  Course PDF: https://www.cs.sfu.ca/~anoop/courses/CMPT-379-Spring-2004/lrk_xform.pdf

### 3.2 Why transform instead of *k*-lookahead parsers

Paper’s practical argument:
1. Computing *k*-lookahead sets is hard.
2. Storing *k*-lookahead only “where needed” still wastes space and complicates the engine.
3. After transform, the **parser is ordinary LR(1)** — simpler space/time analysis.

Objections they acknowledge:
1. **Structure not preserved** (parse tree / production sequence changes).
2. **Size blowup** can be large (sometimes exponential in pathological cases).

They claim for “languages well suited to LR(1)” the blowup is often moderate, and even
badly written grammars often become “reasonable.”

### 3.3 Semantic recovery (critical for slyce!)

Three strategies (paper §1):

**A. Adjust semantic actions** to the new nonterminals/rules  
(e.g. identifier is now “next-to-last scanned symbol” after premature scan).

**B. Grammar covering / internal–external parse** (preferred for compilers):  
- Parse with transformed grammar G′ (internal).  
- Map each G′ production π′ to an original production φ(π′) via a surjection φ.  
- Induce an **external** parse according to original G; run original semantics.  
- Rooted in **grammatical covers** (Gray & Harrison; Reynolds & Haskell).

**C. Lexical merge** of multi-token sequences into single tokens  
(e.g. `:=` as one token so LR(1) can distinguish `:` label vs `:=` assignment).

For slyce auto-rewrite, **B is the architecture**: cleaned LALR grammar + `fromCleaned`
cover mapping to human AST.

### 3.4 Core transformation ideas (paper §2–3)

Illustrative intuition for an LR(2) reduce that needs 2-token lookahead after handle *w*:

1. **Right-context extraction**  
   Pull the conflicting right-context terminal *t* into the grammar structure so that
   deciding the reduce is delayed until *t* is “known” via nonterminal structure.

2. **Premature scanning**  
   Merge the extracted branch with its left neighbor so the parser **shifts *t* earlier**
   (as part of a larger right-hand side / synthetic nonterminal like `[Ab]`).

Example (simplified from paper):

Original (LR(2)):
```
S → A b b | B b c
A → a A | a
B → a B | a
```
Offending: reducing `A → a` vs `B → a` needs second lookahead.

Transformed (LR(1)) idea:
```
S → [Ab] b | [Bb] c
[Ab] → a [Ab] | a b
[Bb] → a [Bb] | a b
```
Decision moves into which synthetic nonterminal was built.

Utility transform used heavily:

**Right-stratification:** split `A → u v` into `A → u [v]` and `[v] → v`  
(breaks long RHS so extraction/scanning apply cleanly).

Lemma style results (paper): language preserved; surjection φ from new productions
onto old ones for covering.

### 3.5 Blowup example from the paper

Pathological LR(2) example `S → b S S | a | a a c` after full extraction+scanning
grows to ~16 rules; paper argues any LR(1) grammar for that language needs ≥12 rules —
blowup is partly **inherent to forcing LR(1) structure**, not pure algorithm waste.

### 3.6 Follow-on academic work

- Mickunas & Schneider related: *On the Ability to Cover LR(k) Grammars with LR(1), SLR(1), …*
- Lee et al.: SLR(*k*) covering for LR(*k*) grammars (transform using the LR parser structure).
- Waterlook tech report (CS-89-65): notes “any LR(*k*) grammar can be rewritten as LR(1)”
  in parser-generation context: https://cs.uwaterloo.ca/research/tr/1989/CS-89-65.pdf
- Canonical LR Wikipedia: “any LR(*k*) grammar with *k*>1 can be transformed into an LR(1)
  grammar” (with back-substitutions for semantics).

## 4. Grammatical covers (mapping trees / derivations)

### 4.1 Why covers matter

Rewrite that only preserves **language** is useless for a typed AST macro: user wants
`Url` / `Json` / `List[Assignment]`, not synthetic nonterminals `[PathSeg/Trail]`.

A **cover** relates parses of G′ to parses of G.

Classic: Gray & Harrison, *On the Covering and Reduction Problems for Context-Free Grammars*,
JACM (covers formally defined ~1969–1972).  
ACM: https://dl.acm.org/doi/pdf/10.1145/321724.321732

Rough idea used in practice:
- Each production of G′ maps to zero or more productions of G (or a homomorphism on
  rightmost derivation sequences).
- **Right cover:** rightmost derivations of G′ map onto those of G so that after parsing
  with G′ you can recover G’s derivation (hence G’s tree shape).
- Mickunas uses a surjection φ: P′ → P (sometimes identity on “same intent” rules,
  sometimes many synthetic rules map to one original).

### 4.2 Cover vs AST transform layers

Two layers often conflated:

1. **Concrete cover:** G′ derivation ↔ G derivation (CFG theory).
2. **Abstract transform:** G (or G′) concrete tree → **user AST** (Product types, enums).

Slyce already does (2) for *conflict-free* models via `FromExtractedType` + reduce kinds.  
For rewrite, need (1) **or** a direct G′ → user AST map that skips materializing G.

Current slyce URL experiment path:
- `cleaned.Url` is hand-left-factored LALR-friendly  
- `fromCleaned: cleaned.Url => model.Url` is the cover/AST map  
- Desired: generate cleaned-like G′ + map automatically from `model.Url`

### 4.3 ANTLR’s approach to “user unaware of rewrite”

ANTLR 4 eliminates **direct left recursion** by rewrite, then **rebuilds parse trees as if
the original left-recursive rule existed** so programmers don’t see the transformed shape.
Source: Parr et al., *Adaptive LL(*) Parsing* (ALLSTAR tech report / OOPSLA-related):
https://www.antlr.org/papers/allstar-techreport.pdf

This is the UX ideal for slyce: rewrite internally, expose human AST.

## 5. What real parser generators do (practice, not full Mickunas)

Most production tools **do not implement the full Mickunas LR(*k*)→LR(1) transform**.
They use a mix of: conflict reporting, default conflict resolution, precedence, optional
GLR, better LR construction (IELR), and **manual** grammar surgery docs.

### 5.1 Yacc / Bison (LALR / IELR / GLR)

**Default conflict resolution (ambiguous or non-LALR grammars):**
1. **Shift/reduce:** prefer **shift** (typical dangling-else).
2. **Reduce/reduce:** prefer the **production listed first** in the grammar file.

Sources:
- IBM z/OS yacc docs on ambiguity rules  
  https://www.ibm.com/docs/en/zos/3.1.0?topic=ambiguities-rules-help-remove
- begriffs, *Practical parsing with Flex and Bison* (2021):  
  https://begriffs.com/posts/2021-11-28-practical-parsing.html

**Precedence / associativity (explicit disambiguation, not full rewrite):**
```
%left '+' '-'
%left '*' '/'
%right UMINUS
```
Resolves classic expr S/R conflicts without changing tree shape much; actions still
attached to original productions.

**IELR(1)** (`%define lr.type ielr`):  
Starts from LALR; **splits states** when merge would lose LR(1) power.  
Result: often full LR(1) language/grammar coverage with fewer states than canonical LR(1).  
Paper: Denny & Malloy, *IELR(1): Practical LR(1) Parser Tables for Non-LR(1) Grammars
with Conflict Resolutions*, SAC 2008.  
https://malloy.people.clemson.edu/publications/papers/sac08/paper.pdf  
Bison docs: https://www.gnu.org/software/bison/manual/html_node/LR-Table-Construction.html

**GLR mode:** accept ambiguous grammars; explore both actions; merge when possible.
Not a rewrite — changes **parser class**.

**What Bison does *not* do:** automatic Mickunas-style grammar rewrite to remove need for
*k*>1 or to auto-left-factor user’s grammar into LALR.

### 5.2 Menhir (OCaml) — canonical LR(1)

- Accepts **LR(1)** grammars (not limited to LALR merges).
- **`%inline`**: macro-like expansion of nonterminals at generation time; can remove
  artificial conflicts **without hand-rewriting** the conceptual grammar.
- Excellent **conflict explanations** in grammar terms (not only automaton states).

Source: https://gallium.inria.fr/~fpottier/menhir/

Implication for slyce: upgrading construction from pure LALR merge to full LR(1) or IELR
**reduces need for rewrite** for some conflicts (those that are LR(1) but not LALR(1)).
It does **not** fix true non-LR(1) surface structure (e.g. needing *k*>1, or genuine
ambiguity).

### 5.3 Happy (Haskell)

- LALR(1) with yacc-like precedence.
- Same human rewrite culture as yacc for conflicts.
- No famous automatic LR(*k*) rewrite.

### 5.4 ANTLR 4 — automatic left-recursion elimination (LL world)

Not LALR, but **best modern example of automatic grammar rewriting + tree repair**:

1. Accepts (almost) any CFG without **indirect/hidden** left recursion.
2. **Direct left recursion** rewritten away before ALL(*) generation.
3. Production order / precedence predicates disambiguate.
4. Parse trees reconstructed for original left-recursive shape.

Classic transform (textbook, also ANTLR paper §2.2):

Direct left recursion:
```
A → A β₁ | … | A βᵣ | α₁ | … | αₛ
```
→
```
A  → α₁ A' | … | αₛ A'
A' → β₁ A' | … | βᵣ A' | ε
```
(EBNF form: `A → (α₁|…|αₛ) (β₁|…|βᵣ)*`)

ANTLR only does **direct** left recursion because general left-recursion elimination can
blow up size and scramble trees (cite Moore 2000; Dragon Book).

Sources:
- Parr, Harwell, Fisher: ALL(*) / ANTLR 4 papers  
  https://www.antlr.org/papers/allstar-techreport.pdf  
  https://www.antlr.org/papers/LL-star-PLDI11.pdf
- Wikipedia: Left recursion  
  https://en.wikipedia.org/wiki/Left_recursion

**For bottom-up LALR, left recursion is usually *desired*** (natural for lists/exprs).
So ANTLR’s main rewrite is **not** the primary tool for slyce’s LALR engine — but the
**pattern** (rewrite + restore user-facing tree) is exactly right.

### 5.5 Manual human rewrites (what docs teach)

Standard conflict-killing rewrites taught with yacc/bison:

| Technique | Fixes | Idea |
|-----------|-------|------|
| Left factoring | common prefix alternatives | `A → α β \| α γ` → `A → α A'`, `A' → β \| γ` |
| Nonterminal cloning | LALR merge false conflicts | copy nonterminal per context (manual state split) |
| Precedence decls | expr / dangling else | external priority, keep grammar “natural” |
| EBNF→BNF expansion | `?` `*` `+` | introduce list/optional nonterminals carefully |
| Token merging | multi-char ops | lexer absorbs `:=`, `->` |
| Layered expr nonterminals | precedence | `E → E+T \| T`, `T → T*F \| F`, … |
| Delay reduce (factor end) | need more right context | similar spirit to Mickunas premature scan |

Left factoring algorithm (Dragon Book style):  
While some nonterminal has two alts with longest common prefix α ≠ ε:  
factor α out to a new nonterminal for the suffixes.

Sources:
- Dragon Book sections on eliminating left recursion / left factoring (LL focus, still used)
- StackOverflow / course notes on Bison shift-reduce resolution
- Debray, *A Quick Introduction to Handling Conflicts in Yacc Parsers* (Arizona PDF)

## 6. Left factoring deep dive (highly relevant to URL path/host)

### 6.1 Definition

If
```
A → α β₁ | α β₂ | … | α βₙ | γ…
```
with α common nonempty prefix of some alts, replace with:
```
A  → α A_α | γ…
A_α → β₁ | β₂ | … | βₙ
```

### 6.2 Why LL needs it; why LR sometimes needs it too

- **LL(*k*):** must choose production from left context + *k* lookahead → common prefixes kill LL.
- **LR:** chooses reduce only after full RHS is on stack → left recursion OK; **common
  prefixes are often fine**.

But LR still fails when:
1. **Different nonterminals** share the same token pattern and only **right context**
   after the common span distinguishes them (host: DomainLabel vs Ipv4Octet; path
   segments vs trailing slash) — classic need for more lookahead or rewrite.
2. **Optional trailing** pieces create shift/reduce (`path+` then optional `/`).
3. **LALR merge** mixes lookaheads that LR(1) would keep separate.

### 6.3 “Left factor across nonterminals” / layered cleaning

Hand-cleaned URL grammar in slyce does something like:
- Factor shared digit/label token structure into disambiguating structure at host level.
- Factor path as “segments with optional trail” into a single nonterminal that absorbs
  the trailing `/` decision.

This is closer to **Mickunas premature scan** + **factoring** than to textbook LL left-factor.

## 7. LALR-specific conflicts and state splitting

### 7.1 How LALR loses LR(1) power

Construction sketch:
1. Build LR(1) item sets (core + lookahead).
2. Merge states with identical **cores** (items without lookahead).
3. Union lookaheads.
4. If union creates shift/reduce or reduce/reduce that pure LR(1) lacked → **not LALR(1)**
   even though **LR(1)**.

### 7.2 Fixes without full language-level rewrite

1. **Use LR(1) or IELR** instead of LALR (Menhir / Bison IELR).
2. **Clone nonterminals** used in different contexts so cores don’t merge wrongly
   (manual split ≈ IELR).
3. **Rewrite grammar** so cores never need conflicting lookaheads.

Wikipedia (LR parser):  
> “This splitting of states can also be done manually and selectively with any SLR or
> LALR parser, by making two or more named copies of some nonterminals.”

### 7.3 IELR(1) as “auto rewrite of the automaton”

IELR does not rewrite the **grammar text**; it rewrites the **state machine** by
splitting. From a *language recognition* view, that’s enough. From an *AST covering*
view, productions are still the user’s — good UX.

If slyce’s conflicts are pure LALR-merge artifacts, **IELR-like construction** may
remove the need for grammar rewrite entirely for those cases.

If conflicts are true non-LR(1) (need *k*>1 as written), need Mickunas-style grammar
rewrite or higher-*k* / GLR.

## 8. Ambiguity vs insufficient lookahead

Critical distinction for auto-rewrite:

| Situation | Language | Grammar | Fix |
|-----------|----------|---------|-----|
| Ambiguous grammar (2 parse trees) | May still be deterministic *if* another grammar exists | Ambiguous | Prefer one tree: precedence, order, predicates; or GLR |
| Unambiguous but not LR(*k*) for any *k* | Not DCFL or needs unbounded look | — | Different parsing paradigm |
| Unambiguous LR(*k*) *k*>1 | DCFL | Not LR(1) as written | Mickunas → LR(1) grammar |
| Unambiguous LR(1) not LALR(1) | DCFL | LALR merge conflict | IELR / LR(1) / clone NTs |
| Unambiguous SLR fail LALR ok | DCFL | Follow too coarse | Use LALR |

**Decidability:**  
- Is G LR(*k*) for fixed *k*? **Decidable.**  
- Exists *k* s.t. G is LR(*k*)? **Undecidable.**  
(Source: Wikipedia LR parser; classic theory.)

So an auto-rewriter that “finds some *k* and transforms” cannot always decide success for
arbitrary CFGs; practical systems detect conflicts for *k*=1 (or small *k*) and either
fail, apply heuristics, or switch parser class.

## 9. Precedence and associativity as lightweight “rewrite”

Yacc-style:

```
E → E + E | E * E | id
```
is **ambiguous**. With `%left +` `%left *` the **automaton** resolves S/R conflicts:
- higher precedence operator → shift or reduce according to priority
- same precedence + left assoc → reduce
- same + right assoc → shift

This is **not** a grammar rewrite in the CFG sense; it is **conflict resolution policy**
that defines a unique parse. Many “natural” expression grammars rely on this instead of
layered `E/T/F` nonterminals.

ANTLR encodes similar intent via **production order + precedence predicates** after
left-recursion elimination.

For slyce models derived from algebraic data types, precedence is less natural unless
annotated (`@left`, `@prec(n)`). Layered types or explicit rewrite may fit better.

## 10. EBNF constructs and list encoding (slyce-relevant)

Human models use:
- `Option[A]` → optional
- `List[A]` / `::` → repetition
- product fields → sequencing
- sealed traits → alternatives

Naïve expansion:
```
OptA → A | ε
ListA → A ListA | ε     // right recursive
// or
ListA → ListA A | ε     // left recursive — better for LR lists
```

**Optional trailing separators / trailers** are classic S/R mines:

```
Path → Seg+ OptSlash
Seg → / Label
OptSlash → / | ε
```

After `Seg+`, seeing `/` is S/R: shift for another Seg? or reduce OptSlash?  
(Depends on whether next is Label or end — needs lookahead into Label vs EOF/query.)

**Left-factored / absorbed form:**
```
Path → Seg PathRest
PathRest → Seg PathRest | / | ε   // or PathAndTrail nonterminal
```
or cleaned:
```
Path → ( / Label )+ ( / )?   // with careful encoding so trail is part of same NT
```

This is the **URL path** issue in slyce v2 RED commit territory.

## 11. Host DomainLabel vs Ipv4Octet (slyce RED)

Pattern:
- Both can look like digit sequences / alnum.
- Distinction may need **extra tokens of lookahead** or **structural** differences
  (dots, length, final TLD vs exactly 4 octets).

If the **lexer** already splits `Ipv4` as one terminal, host conflict disappears.  
If both are composed of smaller terminals, grammar is often LR(*k*) *k*>1 or needs
rewrite that **delays the Domain vs IPv4 reduce** until enough dots/octets seen —
exactly Mickunas “don’t reduce until right context absorbed.”

Cleaned slyce approach: left-factor host into a form that commits later / shares prefix
structure.

## 12. Theoretical vs practical auto-rewrite options for slyce

### Option A — Full Mickunas (heavy)

- Detect non-LR(1) reduces (or LR(*k*) for small *k*).
- Apply right-stratification, right-context extraction, premature scanning.
- Build production map φ for covering.
- Generate reduce functions for G′ that either:
  - build cleaned AST then `fromCleaned`, or
  - emit original-model AST via φ during reduce.

Pros: complete for LR(*k*) grammars.  
Cons: complex; size blowup; hard to implement correctly in a macro; rare in industry tools.

### Option B — Heuristic local rewrites (pragmatic)

Target **common derived-model patterns**:

1. **Optional trailer after list** → PathAndTrail-style absorb.
2. **Common prefix alts on same NT** → left factor.
3. **Same prefix, different NTs** (DomainLabel vs Octet) → introduce shared prefix NT +
   delayed commit (manual pattern generalized).
4. **Expr layers** from `@prec` annotations.

Pros: matches real user models; controllable.  
Cons: incomplete; must not become URL-hardcoded special cases — patterns must be
**grammar-shaped**, not domain-shaped.

### Option C — Stronger automaton (IELR / LR(1))

- Keep human grammar; fix LALR-merge-only conflicts.
- Fail only on true non-LR(1).

Pros: no tree map needed for those cases.  
Cons: doesn’t fix URL-like *k*>1 structure.

### Option D — Dual grammar (current cleaned approach, generalized)

- User writes **desired AST model**.
- Tool synthesizes **parsing model** (or user maintains `cleaned` package).
- Explicit `fromCleaned` (hand or generated).

Pros: honest; debuggable; already working for URL via hand clean.  
Cons: two models unless synthesis is automatic.

### Option E — GLR / general CF

- Accept ambiguity; pick tree by priority or return all.
- Different product goals (not classic LALR linear parse).

## 13. Implementation sketch notes for a future agent

### 13.1 Pipeline (aspirational)

```
Scala AST model
    ↓ extract ExtractedType / GSym
Surface grammar G_surface
    ↓ GrammarValidity (conflict detect)
if LALR(1): codegen reduces → done
if LR(1) not LALR: try IELR/LR1 tables OR clone NTs
if LR(k) k small: try Mickunas-lite / heuristic rewrites → G'
if ambiguous w/ precedence annotations: apply prec policy
else: hard error with conflict explanation
    ↓
G' + cover φ + FromExtractedType reduces for G'
    ↓
ParserImpl tables
    ↓ runtime
tokens → G' tree → φ/fromCleaned → user AST
```

### 13.2 What to store with each rewrite

- Original production id
- New production id(s)
- Cover action: `Id`, `Drop`, `Wrap`, `Concat`, `Choose(n)`, custom AST builder ref
- Whether rewrite is language-preserving + structure-changing

### 13.3 Testing strategy

- Round-trip: strings that parse under cleaned hand grammar must parse under auto G′
  to same user AST.
- Negative: true ambiguity without annotations still **compile error** (RED is good).
- Size metrics: |P′|, |states′| vs baselines.
- Calculator/JSON must remain unchanged (already LALR).

### 13.4 Non-goals (from recent slyce chat)

- Do **not** hardcode `Url` / `PathAndTrail` as special types in `FromExtractedType`.
- Do **not** silently pick shift/reduce without user-visible policy (slyce currently prefers
  hard fail via GrammarValidity — good for typed macros).
- Prefer oxygen.quoted / oxygen.meta over raw Quotes.reflect (PLAN non-negotiable).

## 16. Myths / careful wording checklist

| Myth | Reality |
|------|---------|
| “Any LALR(*n*) grammar is already LALR(1)” | False. Lookahead depth and merge both matter. |
| “Any LALR(*n*) can be rewritten LALR(1) for free” | Language may be LR(1); **same** LALR grammar may need structural change; LALR≠LR. |
| “LR(*k*) languages need LR(*k*) parsers” | False for *k*≥1; transform grammar → LR(1) parser. |
| “Rewrite preserves AST automatically” | False; need cover / tree repair (ANTLR does this explicitly). |
| “Bison auto-rewrites to LALR” | False; defaults resolve conflicts or you rewrite by hand; IELR splits states. |
| “Left factoring is only for LL” | Primarily LL, but LR still uses factoring-like structure for trailers/shared prefixes. |
| “Ambiguous + LALR rewrite = deterministic” | Ambiguity needs policy or multi-parse; rewrite alone doesn’t invent unique meaning. |

## 19. Append: algorithm outlines (pseudo)

### 19.1 Left factor (single NT)

```
function leftFactor(G):
  repeat until fixed point:
    for each A with alts P_A:
      α = longestCommonPrefix of some subset S ⊆ P_A, |S|≥2, α≠ε
      if α exists:
        create fresh A'
        replace those alts with A → α A'
        add A' → suffixes of alts in S
  return G
```

### 19.2 Direct left-recursion elim (LL; not primary for LALR)

```
for each A:
  partition alts into recursive A→A β and base A→α
  replace with A→α A'; A'→β A'|ε
```

### 19.3 Mickunas-lite “premature scan” (conceptual)

```
when reduce A→w conflicts needing terminal t of right-context:
  for each production C→u A v where t ∈ First(v…):
    introduce [A t] / extract t into neighboring structure
    rewrite so t is shifted before deciding A vs competitor
  map new prods to old via φ
```
(Full algorithm is multi-phase with stratification; see paper §3.)

### 19.4 Optional trailer absorb (list + opt sep)

```
// surface
Path = List[Seg] ~ Option[Trail]
// rewritten parsing NT
PathP = Seg+ Trail?
// cover
fromPathP(segs, trailOpt) = Path(segs, trailOpt)
```
Must be driven by **grammar shape** (list field + optional field sharing First sets),
not by type name `Path`.

### 19.5 Nonterminal clone (LALR false conflict)

```
if A used in contexts c1, c2 with incompatible merged lookaheads:
  replace uses with A_c1, A_c2
  duplicate productions of A for each clone
  cover: both map to same AST constructor for A
```

## 20. Append: decision tree for “why won’t this grammar LALR?”

```
Build LALR(1) table
  └─ conflict?
       ├─ NO → done
       └─ YES
            Build canonical LR(1) (or IELR)
              ├─ no conflict → LALR-merge issue
              │     fixes: IELR, NT clone, accept larger tables
              └─ still conflict
                    Try LR(k) for k=2..Kmax (expensive) or inspect patterns
                      ├─ looks like k>1 deterministic → Mickunas / heuristic rewrite
                      ├─ classic expr/dangling-else → prec annotations
                      ├─ optional trailer / common prefix → left factor / absorb
                      └─ multiple trees same string → ambiguity
                            fixes: user policy, GLR, or redesign model
```

## 22. Append: what “equivalent grammar” means

Usually:
- **Weak equivalence:** L(G′) = L(G) (same strings).
- **Cover equivalence:** L same **and** parses of G′ systematically map to parses of G.
- **Structural equivalence:** same productions up to renaming — **not** expected after rewrite.

Slyce needs at least **cover equivalence to the user AST**, which is slightly different
from classical G-cover: final value is a Scala ADT, not necessarily G’s concrete tree.

## 23. Append: CS.SE consensus on LR(k)→LR(1)

Community answers (cs.stackexchange / theory) align with:
- Every DCFL has some LR(1) grammar.
- A **specific** LR(*k*) grammar can be algorithmically rewritten to some LR(1) grammar
  (Mickunas).
- The rewritten grammar is not unique and not size-optimal in general.
- Having *some* LR(1) grammar does not mean *your* natural grammar is LR(1).

## 24. Append: Gray–Harrison cover (why φ works)

Covers formalize: G′ **covers** G if there is a homomorphism on production sequences
such that every string’s G′ rightmost derivation maps onto a G rightmost derivation.
Then a parser for G′ + homomorphism = parser for G with G’s semantic actions.

Mickunas’s internal/external parse diagram is exactly this:
```
input → parser(G′) → prods π′ → φ(π′) → semantics(G)
```

For slyce macro codegen, φ becomes generated Scala functions:
```scala
// conceptual
def reduce_π′(stackValues...): UserAstOrPartial =
  mapCover(φ(π′), stackValues)
```

## 26. Append: risk notes for exponential blowup

When auto-rewriting in a compile-time macro:

- Cap |P′| / |states| growth (e.g. refuse if > 20×).
- Prefer IELR before Mickunas.
- Prefer lexer token merge when conflict is 2-char operator.
- Prefer user `@prec` / `@left` for expr-shaped models.
- Log rewrite steps into optional debug macro dump (like Menhir’s explain).

Mickunas pathological examples show 12–16 rules for tiny LR(2) languages — acceptable.
Nested need for multi-symbol contexts can cascade.
