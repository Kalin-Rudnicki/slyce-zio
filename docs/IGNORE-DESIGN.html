slyce v2 · design brief

How should ignore work?

Open question before implementation. Today we have annotation stubs (ignoreBefore / ignoreAfter / ignoreBetween), an Ignore nonterminal type, and PLAN notes that IgnoreBuiltIn is “omitted from the production.” Those are different mechanisms. This brief lays out options so we can pick a coherent surface API.

whitespace / noise tokens not in the ADT grammar inserts, reduce skips related: VElementList

00 What problem are we solving?

Many grammars want tokens that are required for the language but unwanted in the typed AST — usually runs of whitespace, sometimes comments. Bash wants spaces between words without modeling SpacedWord(ws, word) forever. JSON often wants optional spaces around : and ,.

Non-goal

This is not about “skip invalid input.” Ignored terminals still have to match when present; they just don’t become case-class fields.

Two existing stubs (don’t conflate them)

StubLikely intent
Ignore / IgnoreBuiltIn A field type that is omitted from the grammar production (and maybe from construction). PLAN: “omitted from production.” Empty product edge case: “use Ignored.”
@ignoreBefore[T] / After / Between Annotations that inject optional (or starred) terminals of type T around real structure, without ADT fields.

Recommendation: treat annotations as the main “whitespace” feature; keep Ignore as a separate “this field is not parsed” escape hatch only if we still need it.

01 Shared design knobs (apply to every option)

Which terminal?

Annotation type arg T <: Terminal must be a product terminal with @regex (e.g. Ws matching [ \t\n\r]+).

Optional vs star

Most tools insert (Ws)? if Ws already matches a run (\s+). Alternatively insert Ws* for single-char tokens. Default proposal: optional once (ElementOption-shaped ignore), assuming multi-char runs in the regex.

Reduce / cover

Grammar RHS gains symbols that do not map to case-class fields. Same idea as FieldSource skipping rewrite scaffolding — ignore slots are popped but discarded (or reduce to unit).

Lexer interaction

State-scoped lex already only tries terminals legal in the current state. Ignore terminals become legal wherever the grammar inserts them. No global “skip all Ws.”

02 Attachment options

A — Type-level on products only lean good first slice 

@ignoreBefore[Ws]
@ignoreAfter[Ws]
@ignoreBetween[Ws]
final case class Arr(
  open: `[`,
  body: ElementOption[ArrBody],
  close: `]`,
) extends Json, NonTerminal

Grammar expansion (optional once each):

Arr → Ws?  `[`  Ws?  body?  Ws?  `]`  Ws?
  • ignoreBefore → before first field
  • ignoreBetween → between consecutive fields
  • ignoreAfter → after last field

Does not insert spaces inside ElementList[…] elements. Nested products need their own annotations (or inherit — see option D).

Pros: simple, matches annotation placement as written, greenable for “spaces around punctuation.” Cons: Bash words still need list-internal spacing strategy.

B — Type-level + auto list inter-element convenient surprising? 

@ignoreBetween[Ws]
final case class BashCommand(
  words: NonEmptyElementList[Word],
  end: ElementOption[CmdEnd],
)

Product gaps get Ws?, and any ElementList / NonEmptyElementList field under this product expands as:

words → Word (Ws? Word)*

Pros: Bash becomes natural without SpacedWord. Cons: Magic coupling (“annotation on product affects list encoding”). Harder to have spaces between product fields but not inside a nested list of numbers, etc. JSON ArrBody.tail: ElementList[CommaJson] would get spaces between ,value chunks (usually fine) — also between other lists unexpectedly.

C — Field-level annotations precise more API 

final case class BashCommand(
  @ignoreBetween[Ws]
  words: NonEmptyElementList[Word],
  @ignoreBefore[Ws]
  end: ElementOption[CmdEnd],
)

Meaning proposal:

  • On a list field: ignoreBetween = between elements; ignoreBefore/After = before first / after last element of that list.
  • On a scalar field: ignoreBefore/After = immediately before/after that field’s symbol(s).
  • Type-level annotations can still exist as defaults for all product gaps.

Pros: express exactly Bash vs Arr vs KeyPair without magic. Cons: need field annotation extraction (Oxygen fields already expose annotations); more rules to document.

D — Inheritance / cascade into nested NTs powerful complex

Annotate root Json once; all nested products/lists inherit the same ignore terminal unless overridden. Great for “JSON is space-insensitive everywhere.”

Pros: one annotation for a whole language. Cons: hard to reason about; interactions with rewrite; over-inserts ignore in places that change FIRST sets and conflicts.

E — Explicit VElementList (already sketched) orthogonal 

// Significant separators that *do* appear in a rich list structure
VElementList[Elem, Before, Between, After]
// e.g. Between = `,` for JSON without trailing-comma sugar

This is for visible separators that participate in list structure (and possibly AST via toVList), not for “throw away Ws.” Complements ignore; does not replace it. PLAN still has VElementList expansion as TODO.

F — Global / lexer-level skip classic yacc 

// Conceptual — not in current annotations
// Always drop Ws anywhere the lexer runs, never produce tokens

Simple for free-form languages; fights state-scoped lex and significant-whitespace languages (Python, Bash if newlines are tokens). Not recommended as the only mechanism given slyce’s per-state lexers.

04 Expansion semantics (proposal detail)

Regardless of attachment, the mechanics can be shared:

  1. Resolve annotation type T → ProductTerminal (regex + BuildTerminal).
  2. Allocate a shared ignore NT, e.g. $ign[T.label] with productions T | ε (optional once). Alternative star: list NT of T.
  3. When building a production’s symbol list, interleave ignore NTs per rules.
  4. Product FieldSource only references stack slots of real fields (ignore reduces still push a value, discarded — or special “no push” reduce if we want).
  5. Grammar rewrite / FIRST analysis sees ignore as nullable symbols — usually fine; may create new nullable-overlap cases (watch carefully).
Nullable hazard

Inserting nullable ignore between List[A] and Option[B] can create extra FIRST/FOLLOW mess. Prefer inserting ignore only where the adjacent real symbols already have disjoint FIRST, or treat ignore as “transparent” for rewrite detection (advanced).

05 Suggested decision path

  1. Ship A first — type-level before/after/between on products, optional once, explicit tests (JSON with spaces; a tiny product fixture).
  2. Add C for lists — field-level @ignoreBetween[Ws] on ElementList / NonEmptyElementList so Bash can drop SpacedWord.
  3. Defer D/F — cascade and global skip until A/C are proven.
  4. Clarify Ignore type — either implement “omit field from production” for rare cases, or delete / rename to avoid confusion with annotations.
  5. VElementList stays the path for significant separators (commas you care about in structure), separate epic.
What I need from you
  • Attachment: A only, A+C, B, or something else?
  • Ignore multiplicity: optional once vs star?
  • Should Ws include newlines, or keep newline as a real token (Bash)?
  • Any desire for comments (//…) as a second ignore terminal / union of ignore?
